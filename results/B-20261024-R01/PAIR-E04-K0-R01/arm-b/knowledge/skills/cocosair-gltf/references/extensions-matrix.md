## Reading getExtensionSupport()

`src/air/assets/gltf/loader.ts:95-106` merges `globalDefaults` with instance options (`:96`), builds a throwaway probe context `GLTFParserContext({ asset: { version: '2.0' } }, undefined, resolved)` (`:97`), instantiates handlers in registration order (`:99`), and computes `handler.support?.() ?? { name: handler.name, status: 'supported' }`, stamping the handler name onto the result (`:100-101`). Consequences:

- No `support()` means unconditional `supported`. `KHR_materials_unlit` (`src/air/assets/gltf/extensions/material/unlit.ts:8`, 13 lines, no `support`) and `KHR_texture_transform` (`src/air/assets/gltf/extensions/texture/transform.ts:10`, 20 lines, no `support`) are reported `supported` purely by this default.
- `KNOWN_UNIMPLEMENTED` entries are appended only for names not already covered (`src/air/assets/gltf/loader.ts:103-104`); the array is empty (`:49-51`), so the returned list is exactly the 21 handler entries in registration order.
- Status tracks the currently injected decoders: `setDRACODecoder`/`setMeshoptDecoder`/`setKTX2Transcoder` replace instance options (`src/air/assets/gltf/loader.ts:82-90`) and each decoder handler re-reads them when its `support()` runs - meshopt (`src/air/assets/gltf/extensions/geometry/meshopt.ts:107`) and basisu (`src/air/assets/gltf/extensions/texture/basisu.ts:34`) read `context.options` live, while draco snapshots `const decoder = context.options.dracoDecoder` at factory time (`src/air/assets/gltf/extensions/geometry/draco.ts:61`) and reports from that const (`:64`). Handlers are re-instantiated on every `getExtensionSupport()` call and on every `parseAsync` (`src/air/assets/gltf/loader.ts:99`, `:127-128`), so the snapshot is always taken from the options in force for that call and the three behave identically from a caller's point of view. The same loader reports `decoder-required` before injection and `supported` after; `examples/gltf-meshopt/src/main.ts` proves the flip by importing the shipped `meshopt_decoder.mjs` through a runtime-concatenated URL (`:70-72`), wiring `createMeshoptDecoder` + `setMeshoptDecoder` (`:75-77`), then asserting `support?.().status === 'supported'` for quantization, meshopt and draco handlers (`:94-97`). Its draco/KTX2 probes are explicit mocks that exercise factory construction and capability contracts, not real decodes (`:80-88`). The bare-loader teaching path observes the stable `GLTF_DECODER_MISSING` code (`:159-171`).

## required versus optional in validateRequired

`src/air/assets/gltf/extension-registry.ts:104-124` iterates the union of `extensionsUsed` and `extensionsRequired` (`:106-107`):

| Case                                              | Behavior                                                                                                                                             |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| unknown extension, listed in `extensionsRequired` | throws `GLTFError('GLTF_EXTENSION_UNSUPPORTED', 'unsupported required extension: NAME', NAME)` (`:111-112`)                                          |
| unknown extension, optional                       | silent `continue`: no warning, no report entry (`:114`). Warnings for optional fallbacks come from handlers during load instead (e.g. `draco.ts:83`) |
| handler without `support()`                       | defaults to `supported` and passes (`:116-117`)                                                                                                      |
| non-`supported` status, required                  | throws with `SUPPORT_CODES[status] ?? 'GLTF_EXTENSION_UNSUPPORTED'` and message `required extension NAME: STATUS (REASON)` (`:118-121`)              |
| non-`supported` status, optional                  | `context.warn(...)` with the same text; load continues on the core fallback (`:122`)                                                                 |

## Registration order is hook order

The class doc states registration order defines hook execution order (`src/air/assets/gltf/extension-registry.ts:61-64`); `createHandlers` instantiates factories in array order (`:80-89`). A duplicate handler name throws a plain `Error` `[glTF] duplicate extension handler: NAME` (`:86`), and a missing dependency throws a plain `Error` `[glTF] extension NAME requires unregistered extension DEP` (`:93`). Neither is a `GLTFError`, so `error.code` branching does not catch them. `register` is idempotent by factory identity (`:68-71`); `unregister` returns a boolean telling whether anything was removed (`:72-76`).

## What is not proven

Only `supported` and `decoder-required` (pre-injection) have browser-evidence bindings. `device-dependent` is reachable at runtime from four `support()` implementations behind five extension names - webp and avif from one factory, plus transmission, volume and dispersion - but appears in no catalog entry and no tracked evidence. `fallback` and `unsupported` are never emitted by any shipped handler: they exist only in the type union and the code map. Draco browser decode and KTX2 transcode are not bound to any `capability-status` evidence entry; the catalog's `browser-evidence` level for `KHR_texture_basisu` (`examples/gltf-catalog/capabilities.json:266-282`) cites the `gltf-ktx2-browser.js` script, not `docs/evidence/examples-verified.json`, and the meshopt example's draco/KTX2 probes are mocks by their own comment (`examples/gltf-meshopt/src/main.ts:80-81`). `EXT_materials_bump` reports `supported` unconditionally even where its shader degrades to a flat normal (`bump.ts:6`, `:19`), so that degradation is invisible to `getExtensionSupport()`.
