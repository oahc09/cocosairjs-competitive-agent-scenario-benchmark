# What is actually shipped

Three names reach the application: `sp` (the namespace alias emitted as `index$2 as sp`), `loadWasmModuleSpine`, and through `sp` the real classes `Skeleton`, `SkeletonData`, `SpineAnimationCacheMode`, `SpineMaterialType`, `SpineSocket`, `vertexEffectDelegate` and the assembler. They resolve in the single `export { ... }` block of `build/cocosair.module.js` (currently `:161574`). Wiring is thin and official: `src/exports/spine.ts:3` exports `sp`, `:5` re-exports `loadWasmModuleSpine`, and `src/cocos/spine/index.ts:48-52` re-exports `./skeleton`, `./skeleton-data`, `./vertex-effect-delegate`, `./assembler` and `./lib/spine-version`, with `:54` exporting the `spine` lib object itself.

That is the whole honest story: the code closure and the type surface are in, the runtime backend is not.

# The BLOCKED chain, end to end

1. The web path has only a wasm/asm backend. `src/cocos/spine/lib/spine-core.js` is 177 lines containing enums and stubs (`MixBlend`, `MathUtils` and friends) with zero occurrences of `SpineWasmUtil` or `wasmUtil`; the complete type face, including `class wasmUtil`, lives in `src/cocos/spine/lib/spine-core.d.ts` (1498 lines) as a declaration-only artifact. `docs/notes/spine-asset-sourcing.md:16-20` records those measurements against the upstream baseline.
2. Real injection happens only after emscripten instantiation. `src/cocos/spine/lib/spine-define.ts:91-94` is `overrideClass(wasm)`, which assigns `spine.wasmUtil = wasm.SpineWasmUtil`, sets `spine.wasmUtil.wasm = wasm` and calls `spineWasmInit()`; `:328-329` expose `overrideSpineDefine(wasm)`. Nothing in the default AIR build ever calls them.
3. The emscripten artifacts are absent from the snapshot. `docs/notes/spine-asset-sourcing.md:25-34` checks four sources - `cocos/spine/lib/`, the repository `external/` root, `native/external/emscripten/` (the target of the `external:emscripten/*` virtual modules) and installed `@cocos/*` packages - and finds no `.wasm`, `.asm.js` or `.js.mem` in any of them.
4. The build swaps the entry rather than failing. The module override table in `cc.config.json` maps `cocos/spine/lib/spine-instantiate.ts` to `src/cocos/spine/lib/air-spine-instantiate-js.ts`; the four official files `spine-instantiate.ts`, `spine-instantiate-3.8.ts`, `spine-instantiate-4.2.ts`, `spine-instantiate-dynamic.ts` stay byte-identical in the repository but outside the default closure. Without the override, rollup fails on the missing external file.
5. The shim degrades every call. `src/cocos/spine/lib/air-spine-instantiate-js.ts:26-52` installs `spine.wasmUtil` as a table whose methods are all `noopThenNull` (`:31-34`: warn once, return null) and whose `wasm` field is `{ HEAPU8: new Uint8Array(0) }` (`:36`). Stubbed names, `:37-50`: `spineWasmInit`, `spineWasmDestroy`, `freeStoreMemory`, `createStoreMemory`, `querySpineSkeletonDataByUUID`, `createSpineSkeletonDataWithJson`, `createSpineSkeletonDataWithBinary`, `registerSpineSkeletonDataWithUUID`, `destroySpineSkeletonDataWithUUID`, `destroySpineSkeleton`, `getCurrentListenerID`, `getCurrentEventType`, `getCurrentTrackEntry`, `getCurrentEvent`. `:54` runs the install at import time; `:56-64` exports `waitForSpineWasmInstantiation()` which optionally applies `_CC_SPINE_VERSION` through `setSpineVersion` when the build exposes it, warns and resolves.
6. The warning exists because the upstream call sites have no guards. `src/cocos/spine/skeleton-data.ts:212` calls `querySpineSkeletonDataByUUID` bare, `:224` calls `createSpineSkeletonDataWithJson`, the binary branch at `:226-234` calls `createStoreMemory`, indexes `spine.wasmUtil.wasm.HEAPU8` and calls `createSpineSkeletonDataWithBinary`; `src/cocos/spine/skeleton-cache.ts:173` caches `spine.wasmUtil.wasm.HEAPU8` at module scope and `:383`, `:473` call `destroySpineSkeleton`; `src/cocos/spine/assembler/simple.ts:180` touches `HEAPU8` directly. The stub object exists precisely so those lines keep type-checking and evaluating.

Observable result: `SkeletonData.getRuntimeData()` (`src/cocos/spine/skeleton-data.ts:199-237`) returns null - the cache lookup misses, the json branch gets null, the binary branch writes into a zero-length `HEAPU8` view and still gets null - and `Skeleton._updateSkeletonData()` returns at `src/cocos/spine/skeleton.ts:791` (`if (!this._runtimeData) return;`) with no exception, no log beyond the one warning, and no draw list. The node, the component and the editor-visible properties all behave normally, which is why the failure reads as "the skeleton is silently empty".

# loadWasmModuleSpine is not a fix

`src/cocos/spine/index.ts:127-136` gates everything on `BUILD && LOAD_SPINE_MANUALLY`; the flag is declared `false` in `cc.config.json`, so the default build returns `Promise.resolve()` immediately and never reaches `waitForSpineWasmInstantiation`. Even with the flag on, the awaited function is the shim at `:56-64`, which resolves after warning. Separately, `src/cocos/spine/lib/instantiated.ts:30-32` registers `waitForSpineWasmInstantiation` on the game post-infrastructure delegate when `!JSB && (!BUILD || !LOAD_SPINE_MANUALLY)`, and `src/cocos/game/game.ts:499` declares that delegate with `:817` dispatching it, so in a normal web boot the warning fires once during startup whether or not you ever add a skeleton. Treat "awaited the spine loader and it resolved" as no evidence at all; `docs/reference/web-features.md:13` is the general rule - source present, bundled and deployed assets are three different claims.

# Unblock checklist

`docs/notes/spine-asset-sourcing.md:43-47` states it in order: obtain the emscripten artifacts matching the baseline (per version, `spine.wasm.js`, `spine.wasm`, `spine.asm.js`, `spine.js.mem`), place them as deployed assets next to the bundle instead of inside it, then delete the spine override rule and `src/cocos/spine/lib/air-spine-instantiate-js.ts` to return to official behaviour, and only then add a `spine-basic` example with the json, atlas and texture trio loaded by `loadRemote` plus animation, skin and event assertions and a three-browser matrix. `:51-56` records the owner closure: the same external-binary gap as the physics and webgpu backends, closed as "product surface verified, example surface not delivered", with the shim kept deliberately. `docs/notes/port-spine-and-billboard-decisions.md:5` is the ruling itself. `docs/manual/2d-assets-and-effects.md` carries the subsystem table row that says export surface present, browser evidence none.

Nothing above changes if you set `LOAD_SPINE_MANUALLY` to true in a private build; it only moves which warning you get.
