# Contracts

- `Scene extends Node`. A scene is the tree root; call `scene.addChild(node)`. `app.run(newScene)` and `director.loadScene` route through `runSceneImmediate`, which destroys the previous scene; its children are destroyed with it. `director.getScene()` is the live scene; `find` defaults to it. Tables: [node-ops.md](node-ops.md).
- Component lifecycle runs in this fixed order: `__preload` -> `onLoad` -> `onEnable` -> (first frame) `start` -> `update(dt)` -> `lateUpdate(dt)` -> `onDisable` -> `onDestroy`. `onLoad` runs before any `start`; `start` runs before the first `update`; `dt` is in seconds. `active=false` stops `update` scheduling, not just rendering. [node-ops.md](node-ops.md).
- `node.destroy()` is deferred and narrow: it marks the object `ToDestroy`; the real teardown runs at end of frame in `_destroyImmediate` -> `_onPreDestroyBase`, whose `this._eventProcessor.destroy()` call clears this node's OWN node-event listeners only. The exception is a scene switch: `runSceneImmediate` calls the old scene's `destroy()` and then `CCObject._deferredDestroy()` within the same call (`director.ts:446, :464`), so after `app.run(newScene)` the previous scene already reads `isValid === false`. `input.on`/`Input.EventType` subscriptions, DOM `addEventListener`, `director`/`game` events and callbacks registered on OTHER nodes are out of scope and must be released explicitly (the `scene-switch-reentry` example unsubscribes `input.on` in `onDisable`). [node-events.md](node-events.md).
- `addChild(child)` returns void; do not chain. `setScale(...)` and the `scale` getter act on LOCAL scale; `worldScale` multiplies the parent chain (setting world scale back-solves local). `setParent(value, keepWorldTransform = false)` keeps the child's local transform by default. [node-ops.md](node-ops.md).
- Layers are a bit mask in `node.layer` (default `Layers.Enum.DEFAULT`) tested against `camera.visibility`; a mismatch draws nothing, and the two passes test it differently: the 3D render queue requires containment, `(visibility & node.layer) === node.layer` (`src/cocos/rendering/scene-culling.ts:198`), while the 2D path uses the non-zero test `visibility & node.layer` (`src/cocos/2d/renderer/batcher-2d.ts:265`), so an OR-ed multi-bit `node.layer` must be wholly inside the 3D mask or the 3D pass culls it. The engine default camera mask (`CAMERA_DEFAULT_MASK`) already includes DEFAULT and every user bit (0-19), so a default Camera draws DEFAULT-layer and registered-custom-layer nodes without touching `visibility`; only nodes moved to an excluded bit or a replaced mask go unseen. Register custom layers through `Layers.addLayer(name, bit)` and build masks with `makeMaskInclude`/`makeMaskExclude`; do not hand-OR reserved bits. Bit numbers and the reserved range: [layers.md](layers.md).
- Scene globals (`ambient`, `fog`, `skybox`, `shadows`, `octree`, `skin`, `lightProbeInfo`) are writable config objects reached via `scene.globals`, with a two-phase sync. Before activation edits are staged on the config fields; scene activation (`_activate` -> `_globals.activate`, `scene.ts:204`, skipped in TEST) binds them to the render resources on `director.root.pipeline.pipelineSceneData` (members `ambient`/`fog`/`skybox`/`shadows`/`octree`/`skin`/`postSettings`/`lightProbes`, `pipeline-scene-data.ts:107-115`) and pushes the staged values. After activation the member setters write the bound resource directly (each setter guards `if (this._resource)`), so post-`run` edits apply too. `scene.renderScene` exposes neither ambient nor fog nor skybox; read effective values from `scene.globals` or the bound `pipelineSceneData` members. [scene-globals.md](scene-globals.md).
- Refcount: `Asset.addRef()` increments `_ref` (`asset.ts:316-319`); `decRef(autoRelease = true)` decrements only while `_ref > 0` (`asset.ts:331-334`) and, when `autoRelease`, queues a release attempt through `releaseManager.tryRelease` (`asset.ts:335-336`). Nothing frees synchronously: the free runs on the next tick and only while the count is zero or circular references are all that remains (`release-manager.ts:224-229, :249-253`). A loaded `SceneAsset` (a thin wrapper holding `.scene`) follows the same rule. `Scene.autoReleaseAssets` defaults to `false`; on switch away the release manager calls `decRef(TEST || oldScene.autoReleaseAssets)` on the old scene's dependencies (`release-manager.ts:179, :189`), so leaving it `false` keeps those assets resident until you release them. [scene-globals.md](scene-globals.md).
